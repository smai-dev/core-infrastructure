# Certificate and Internal TLS Baseline

This directory defines the certificate-management foundation for the core
Kubernetes platform.

## PKI separation

Caddy and the Kubernetes cluster use separate certificate authorities.

Caddy remains responsible for host-facing HTTPS such as:

    git.core.home.arpa

The Kubernetes internal PKI is used for service-to-service TLS inside the
cluster.

The Caddy CA private key must not be copied into Kubernetes.

## cert-manager

cert-manager is installed declaratively through Flux from its OCI Helm chart.

The chart version is pinned in Git. Upgrades must be explicit Git changes.

## Cluster PKI

The internal hierarchy is:

    core-selfsigned-bootstrap
              |
              v
        core-root-ca
              |
              v
           core-ca
              |
              v
      workload certificates

`core-selfsigned-bootstrap` exists only to create the root CA.

Application certificates should reference:

    name: core-ca
    kind: ClusterIssuer

## Root CA

The root CA private key is generated by cert-manager and stored only in the
Kubernetes Secret:

    cert-manager/core-root-ca

The private key must never be committed to Git.

The root CA is intentionally long-lived and automatic renewal is disabled.
Root CA rotation must be a deliberate maintenance operation.

The K3s recovery backup protects the cluster state containing this Secret.

## Service certificates

A service that requires TLS should normally request a certificate with DNS
names matching its Kubernetes Service identity.

Example:

    apiVersion: cert-manager.io/v1
    kind: Certificate
    metadata:
      name: example-api
      namespace: platform
    spec:
      secretName: example-api-tls
      issuerRef:
        name: core-ca
        kind: ClusterIssuer
      dnsNames:
        - example-api.platform.svc
        - example-api.platform.svc.cluster.local

Application Pods can mount the generated Secret or reference it through the
controller that terminates TLS.

## Trust

Certificates issued by the internal CA are private certificates.

Applications must explicitly trust the core root CA.

Broad trust-bundle distribution is intentionally deferred until multiple
platform services require it.

## Public and LAN-facing names

Certificates for host-facing names under:

    core.home.arpa

remain part of the Caddy-facing infrastructure unless a future architecture
requires otherwise.

## Security

Never commit:

- certificate private keys;
- CA private keys;
- manually exported Kubernetes TLS Secrets;
- passwords or external CA credentials.

Git should contain Certificate, Issuer, and controller configuration only.
